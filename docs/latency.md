# 执行记忆与延迟优化

## 先区分两个上下文

OpenWAM 的语言条件决定底层动作；Agent 的执行上下文用于规划、理解当前进度和确认交接。缓存 OpenWAM 的语言 K/V 不会自动让 Codex 记住上一次判断，也不能消除云端视觉请求的等待。

0.3 中每次 Codex 判断都是独立请求，包含当前任务、起始和最新观测，不包含前几轮视觉判断。0.4 仍保持隔离的模型调用，但显式提供有界的语义记忆，不依赖无限增长的聊天会话。

## 已实现的优化

### 有界执行记忆

内置 `VisionVerifier` 默认携带当前任务的最近 3 次判断，以及任务总览、已完成数量、最近完成步骤和即将执行步骤。近期判断保留观测时间、verdict、原因与证据摘要；补充上下文最多 8192 UTF-8 字节。长历史字段明确标为 excerpt/truncated，超出预算的总览字段记录在 omitted_fields。当前子任务指令、成功条件、约束、现场规则和本轮硬件信息仍完整传入，不参与历史裁剪。

例如第二轮知道“上一轮物体仍在夹爪中，尚未释放”，便可围绕新画面更新判断。旧 verdict 明确标为可出错的历史，不会被程序直接复用为本轮成功。新任务/重试清空旧尝试的判断；新 run 清空全部记忆。已完成账本也不代替对先前成果的当前视觉检查。

这是带记忆的增量推断策略，没有训练新的模型，也不是已经验证有效的示范 ICL 算法。它可能减少重复分析，也会增加输入 token；实际速度和准确性需要对照实验。

### 一次请求检查多个时间点

配置 `batch_verification: true` 后，事件候选到达且动作队列处于交接状态时，先采集原定数量的新观测，再在一次请求中逐组判断。默认仍是两组，间隔至少 300 ms。起始画面只传一次，两组最新画面都传入；每组都必须满足成功条件才可切换。没有候选的定期巡检保持单组检查。

原流程：检查完成 → 再取图 → 再检查稳定 → 下一任务前置检查。
窗口流程：取两组图 → 一次检查两组 → 下一任务前置检查。

这减少串行请求和重复基准画面，不保证单次请求耗时更短。重复确认本就不是统计独立投票；窗口确认也不能宣称与旧检查等效的物理误判率。默认关闭，可通过配置做对照。候选信号、看门狗上限、新鲜度、下一任务前置检查、交接要求和取消逻辑继续生效。

### 传输与可观测性

Codex 适配器可通过官方 `model_instructions_file` 配置为结构化规划/判断使用专用的简短基础说明，减少默认编程角色的输入开销。当前任务规则、模型选择、low 推理等级、只读沙箱和禁用工具的约束继续保留；不修改用户的全局 Codex 配置。该选项默认关闭：输入 token 减少不保证总延迟更低，仍需验证判断质量。CLI 和重放脚本用 `--compact-instructions` 做对照，Python 使用 `compact_instructions=True`。[官方机制说明](https://openai.com/index/unrolling-the-codex-agent-loop/)

Vela 相机 JPEG 请求并行读取，最多 4 路并发，结果严格按声明的相机顺序排列；任一路失败不返回部分观测。不额外缩图或降低画质。

执行日志分开计时取图、动作执行、前置检查、普通检查和窗口检查。取图记录快照等待、各相机传输耗时及字节数；模型记录输入长度、图像大小、总耗时与 CLI 可用的 token 使用量。`cached_input_tokens` 大于零可以说明服务报告了缓存输入，不能据此声称机器人任务记忆已被缓存。模型总耗时尚不能拆成纯网络、排队和纯推理时间。

## 配置与对照

在原有 profile 顶层添加：

```json
{
  "verification_memory": true,
  "batch_verification": true,
  "confirmations": 2,
  "confirmation_interval_ns": 300000000
}
```

`verification_memory` 默认为 true；设为 false 可关闭历史信息。`batch_verification` 默认为 false，旧自定义 Monitor 不受影响。
保留已校准的 `completion` 和 `visual_watchdog_chunks` 配置。不要仅为速度把确认次数改为 1 或删除硬件告警。

查看新运行各阶段计时：

```bash
agenticwam inspect /path/to/run
```

源码仓库附带只读画面重放脚本。它会向指定 Codex 模型发送录制画面，消耗模型额度，但不加载机器人后端、不发送动作。选择原日志中同时存在 succeeded verification 和随后 completion_check 的步骤；rules 使用该录制运行实际使用的 verification 规则。

```bash
PYTHONPATH=src python scripts/benchmark_verification.py \
  --journal /path/to/recorded-run --rules /path/to/verification-context.json \
  --step-id STEP_ID --repetitions 3 --output /path/to/benchmark.json
```

脚本比较无记忆逐次检查、带记忆逐次检查、带记忆窗口检查，交替实验顺序，保留每次 verdict 和 token 统计。原日志判定只作历史，不是真值；物理正确率需人工或独立评价器标注。

## 算法研究方向与边界

更有针对性的研究问题是：在固定交接误判风险下，如何用有限上下文和尽量少的昂贵模型调用完成长任务。

1. **示范条件化的进度判断。** 从独立标注的成功、失败和接近完成但尚未完成的片段中，按当前任务和场景检索少量支持例子。比较当前短时序与示范的进度，判断“仍在执行、进入交接阶段、异常”。不能只按画面相似度检索而忽略目标物体和槽位。直接把例子塞进每次 Codex prompt 可能增加延迟；更值得测试的是冻结视觉编码器加局部序列匹配，或用教师判断训练一个轻量验证器。
2. **自适应调用大模型。** 轻量判断正常且有进展时沿用当前子任务；进入交接、偏离示范、证据冲突或超过巡检间隔时调用昂贵验证器。阈值应在独立数据上校准，并保留未知分布回退。当前版本没有用未校准分数跳过原有巡检。
3. **预测与现实的一致性。** 若后端暴露 WAM 的未来特征，可检测实际观测是否偏离预测，辅助决定提前重规划。预测吻合只说明执行较符合预期，不证明盘子进入正确目标槽位。

这些方向已有相关工作，不能仅凭组合就宣称新颖性：[ICRT 的示范上下文学习](https://arxiv.org/abs/2408.15980)、[AAC 的自适应动作长度](https://arxiv.org/abs/2604.04161)、[WAM 预测与现实验证](https://arxiv.org/abs/2605.06222)。其中后两者主要处理底层动作执行时长，和本框架高层“何时更换子任务、何时请求语义判断”并不完全相同。

0.4 完成的是有界记忆、时间窗口判定和测量基础；未实现示范编码器、学得的完成检测器、可靠的不确定性校准或机器人 demonstration ICL。发表所需的跨任务、失败案例、消融和物理实验仍需完成。
